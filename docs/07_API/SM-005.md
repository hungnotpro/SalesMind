# SM-005 — Message Ingestion API

## Overview

`POST /api/v1/messages` is a generic, source-agnostic intake endpoint
for the SalesMind message-processing pipeline. It accepts a normalized
message envelope and runs it through the existing
`MessageProcessingService` (the same application pipeline used by the
in-memory and PostgreSQL test paths).

## Architecture

```
HTTP Transport (server.ts)
        ↓
Message Ingestion Controller (messages.ts)
        ↓
Request Validation (validation/messageRequest.ts)
        ↓
MessageProcessingService (existing)
        ↓
Repository Interfaces (existing)
        ↓
PostgreSQL
```

The HTTP layer is intentionally thin. It does not contain business logic,
parsing logic, or persistence logic. The controller only validates the
inbound envelope and translates the pipeline result into a JSON response.

## Endpoint

### `POST /api/v1/messages`

#### Request

```json
{
  "source": "manual",
  "externalMessageId": "msg-001",
  "externalConversationId": "conversation-001",
  "receivedAt": "2026-08-11T10:00:00+07:00",
  "sender": {
    "name": "a.Long",
    "phone": "0904813024"
  },
  "text": "55 bơ:10 cái\nCK 5%\nTiền mặt\ngiao trong ngày"
}
```

| Field | Required | Type | Notes |
|-------|----------|------|-------|
| `source` | yes | string | Identifies the upstream channel (e.g. `manual`, `zalo`). Non-empty. |
| `externalMessageId` | yes | string | Stable deduplication key. Non-empty. |
| `externalConversationId` | yes | string | Belongs to a `Conversation`. Non-empty. |
| `text` | yes | string | Raw message body. Non-empty after trim. |
| `receivedAt` | no | string | ISO-8601 timestamp. Defaults to `now()`. |
| `sender.name` | no | string | Optional customer name. |
| `sender.phone` | no | string | Optional customer phone. |
| `metadata` | no | object | Opaque JSON object. |

Unknown top-level fields are rejected with `400 VALIDATION_ERROR`.

#### Response (201 Created)

```json
{
  "success": true,
  "data": {
    "messageId": "...",
    "correlationId": "...",
    "conversationId": "...",
    "customerId": "...",
    "orderId": "...",
    "reviewRequired": false,
    "reviewReasons": [],
    "intent": "order",
    "itemCount": 7,
    "createdAt": "2026-08-11T10:00:00.000Z"
  },
  "meta": {
    "idempotentReplay": false
  }
}
```

#### Error responses

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "source: source is required and must be a non-empty string",
    "requestId": "...",
    "details": [
      { "field": "source", "code": "required", "message": "..." }
    ]
  }
}
```

| Status | Code | When |
|--------|------|------|
| 400 | `VALIDATION_ERROR` | Inbound envelope failed validation. |
| 400 | (invalid JSON) | Body is not parseable JSON. |
| 415 | `VALIDATION_ERROR` | `Content-Type` is not `application/json`. |
| 500 | `PROCESSING_FAILED` | The pipeline raised an exception. |
| 404 | `NOT_FOUND` | Unrecognized route. |

## Idempotency

The same `(source, externalMessageId)` pair is processed only once.

- The controller performs a pre-flight check against the message
  repository before invoking the pipeline. If a prior message exists,
  the controller returns the existing result with `meta.idempotentReplay: true`.
- The pipeline itself is idempotent at the database level
  (`UNIQUE(source, external_message_id)` for messages and
  `UNIQUE(source, external_conversation_id)` for conversations).

## Transaction boundary

The HTTP controller does **not** start a transaction. The application
service is invoked through a `PipelineInvoker` callback that wraps the
existing `withTransaction(pool, ...)` helper. The transaction boundary
is owned by the application layer, not the HTTP layer.

## Out of scope

- Zalo webhook authentication
- Dashboard / frontend
- LLM provider integration
- TTL / rate limiting
- OAuth / API keys
- Orders / tasks / customers GET endpoints (separate feature)

These are layered concerns that sit in front of (or alongside) this
controller. They are out of scope for SM-005.

## Testing

```bash
npm test                              # all 241 tests
npm run test:integration              # all integration tests (incl. this one)
npx vitest run tests/sm005.test.ts    # API unit tests only
npx vitest run tests/integration/sm005.test.ts  # API + real PostgreSQL
```

The integration test boots a real HTTP server backed by the real
`MessageProcessingService` running against PostgreSQL and verifies:

1. Successful ingestion returns 201.
2. Idempotent replay returns the same `orderId` on a second POST.
3. Message + conversation + order rows exist in PostgreSQL after success.
4. Validation failures return 400 with `VALIDATION_ERROR`.
